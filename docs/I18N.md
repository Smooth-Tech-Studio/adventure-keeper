# Langues (i18n)

L'application parle français et anglais. Ce document fixe les décisions, les
conventions pour traduire un écran, et comment ajouter une langue.

## Décisions (13 octobre 2026)

- **Langues** : français (langue source) et anglais.
- **Bibliothèque** : [i18next](https://www.i18next.com/) + `react-i18next`.
- **Langue choisie** : le profil (`users/{uid}.locale`) l'emporte ; sinon le
  dernier choix sur l'appareil (`localStorage["ak-language"]`), sinon le
  navigateur, sinon le français. Changer de langue connecté l'écrit dans le
  profil ; un invité garde son choix sur l'appareil. Un compte créé prend la
  langue du moment.
- **Contenu intégré** (sorts, classes, dons…) : affiché dans la langue **du
  lecteur**. Le moteur ne manipule que des identifiants ; ce que les joueurs
  écrivent et les blocs copiés (objets, `packContent`) restent tels quels.
- **Packs** : un champ `language` facultatif sur `ak-pack/1`, et des
  traductions dans le pack lui-même (`translations`) ; un badge quand le
  lecteur n'y trouve pas sa langue.

## Conventions

- Les textes vivent dans `apps/web/src/locales/<langue>/<namespace>.json` et
  sont déclarés dans `apps/web/src/i18n/index.ts` (`resources`). Le français
  type les clés (`i18n/i18next.d.ts`) : une clé absente ou mal orthographiée
  casse `tsc`.
- Un test (`i18n/locales.test.ts`) vérifie que chaque langue a les mêmes clés
  que le français, et qu'elle garde chaque `{{variable}}` et chaque `<balise>`.
- Un namespace par grand domaine (`common`, `auth`, `home`, `profile`, puis
  `campaigns`, `characters`, `session`, `packs`…). `common` porte ce qui sert
  partout : navigation, actions, messages de validation.
- Dans un composant : `const { t } = useTranslation("profile")`. Hors React
  (messages d'erreur, tri) : `i18n.t(...)` ou `currentLanguage()`.
- Texte avec mise en forme ou lien : `<Trans>` avec des balises nommées
  (`<strong>…</strong>`), jamais des morceaux de phrase recollés.
- Pluriels : suffixes i18next (`clé_one`, `clé_other`) et `{ count }`.
- Schémas Zod : le message est une clé (`"validation.emailRequired"`) ;
  `FormMessage` la traduit (`translateKey`), et laisse passer tel quel un texte
  qui n'en est pas une, le temps que tous les formulaires soient traduits.
- Dates, nombres, tri : jamais `"fr-FR"` en dur — `currentLanguage()` et
  `compareText` (`lib/sort.ts`).
- Les tests E2E tournent en `fr-FR` (`playwright.config.ts`) et cherchent les
  textes français.

## Moteur et catalogues

- `system-dnd2024/src/locale.ts` : `setLocale` (appelé par `applyLanguage`),
  `withLocale` pour les tests, `pick({ fr, en })` pour un texte généré,
  `localized({ fr, en })` pour une table, `localizedList` pour une liste triée
  par langue, `translateById` / `translateTree` pour poser l'anglais sur des
  définitions sans changer leur forme. L'anglais du contenu du SRD vit à côté
  du français, dans chaque fichier du pack de base (`src/srd/*.json`,
  `translations.en`), au format des traductions de packs.
- Les identifiants et les valeurs enregistrées restent français (options de
  lignée, variantes de sorts) ; l'affichage passe par `speciesOptionLabel`,
  `subclassSpellVariantLabel`.
- Distances en pieds et poids en livres en anglais (`formatDistance`,
  `formatWeight`) ; pièces po/pa/pc → gp/sp/cp (`COIN_ABBR`). Les champs saisis
  en mètres ou en kilos se convertissent à l'affichage et à la saisie.
- `locale.test.ts` passe chaque constante exportée en anglais et refuse tout
  reste de français.
- Catalogues (sorts, équipement) : même forme, `src/srd/*.json` du moteur,
  appliqués au chargement (`systems/dnd2024/lib/spells.ts`,
  `systems/dnd2024/lib/equipment.ts`) ; test `srd/en-catalogs.test.ts`.
- Hors React : `tr(clé, valeurs)` (`@/i18n`) ; un module de données expose des
  getters (`get label() { return tr(...) }`) pour suivre la langue.

## Ajouter une langue

Ajouter `locales/<langue>/` de l'app, et une entrée `translations.<langue>`
dans chaque fichier `src/srd/*.json` du moteur (et `LOCALES` dans
`packages/locale`).
